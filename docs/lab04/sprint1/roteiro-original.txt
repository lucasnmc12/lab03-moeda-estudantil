1. Objetivo da Sprint
Esta é a primeira sprint da Release 2, que dá continuidade ao sistema entregue na Release 1 (Laboratório 03). Também é preciso configurar o envio automático de emails de confirmação, com um template específico para o professor e outro para o aluno, e preparar uma demonstração funcional (em laboratório ou em vídeo, caso o ambiente não possa ser reproduzido na aula).

3. Conceitos-chave
3.1 Envio de moedas como uma transação
O envio de moedas é uma operação que, ao mesmo tempo, debita o saldo do professor, credita o saldo do aluno e registra uma transação (EnvioMoeda) com o motivo do reconhecimento. Essas três ações devem ocorrer de forma atômica: se qualquer uma delas falhar, nenhuma das outras deve ser persistida. Em Spring, isso é obtido anotando o método de serviço com @Transactional.
3.2 Extrato como consulta sobre o histórico de transações
O extrato não é uma nova entidade: é uma consulta sobre as transações já existentes, filtradas por usuário. Para o professor, o extrato lista os envios que ele realizou; para o aluno, lista tanto as moedas recebidas quanto as trocas por vantagens (estas últimas serão implementadas em sprints futuras, mas a consulta já deve estar preparada para incluir ambos os tipos).
3.3 Envio de email com template
Um template de email separa o texto fixo (saudação, estrutura, encerramento) dos dados variáveis de cada envio (nome do destinatário, quantidade de moedas, motivo). Isso evita montar a mensagem inteira por concatenação de strings dentro do código de negócio, e facilita manter dois templates distintos, um para o professor (confirmando que o envio foi realizado) e um para o aluno (avisando que recebeu moedas).

6. Erros Comuns e Dicas
- Esquecer @Transactional no envio de moedas. Sem essa anotação, uma falha no meio da operação pode debitar o professor sem creditar o aluno.
- Misturar o texto dos dois templates de email. Revisem se o conteúdo enviado ao professor é realmente uma confirmação de envio, e o conteúdo enviado ao aluno é realmente uma notificação de recebimento.
- Testar apenas o caminho feliz. Lembrem de testar o caso de saldo insuficiente, que deve ser rejeitado com uma mensagem compreensível.
- Deixar credenciais de email reais no código versionado. Usem variáveis de ambiente ou um arquivo de configuração fora do controle de versão.
- Gravar o vídeo de demonstração fora do horário de aula. Isso não conta para o critério de commits durante a aula.
